# HTTP/RPC 按客户端和服务端组织

## 背景与选择

仓库将包含更多模块，因此公开头文件、实现和测试按能力归属。
HTTP/RPC 按两端合并；S3 保持独立客户端模块，依赖 HTTP Client。

保留聚合库会继续让调用方链接另一端；完全重写运行时则增加状态与协议迁移风险。
采用两个独立动态库，各自编入 RPC 实现，复用内部 `http_common` 对象代码。
共享代码不持有两端业务 owner；vendor 的 target 分组保持在 vendor 下。

## 影响与权衡

- `CHttp::Client`、`CHttp::Server` 分别提供本侧 HTTP/RPC；`CHttp::S3` 提供独立 S3 API。
- 公开声明位于各模块 `include/`；共享协议类型位于 `http_common/include/`。
- 共享对象代码分别进入两端动态库，会增加同时部署两端时的代码体积，避免引入第三个 HTTP 运行库依赖。
- 请求、Session、middleware、TLS、RPC 和 S3 的状态归属、所有权与错误语义保持。
- 使用方必须更新头文件和目标名并重新编译；迁移不涉及业务数据格式。
- CMake 使用原生命令和直接配置变量，不保留旧目标别名或自定义校验包装。

## 验证与迁移

通过既有 HTTP/RPC/S3 运行测试和 C++ 头文件测试验证行为，检查各动态库的链接依赖。
Windows 采用与 Salts 相同的 MSVC preset。迁移时替换对应包并重编调用方；
需要回滚时恢复重构前的完整包与消费工程版本。
